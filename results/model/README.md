## Why STRIP wins at small M and both modes converge at large M

The array always has 64 multipliers, but an output tile can only use as many PE rows as the matmul has rows. In FULL mode a tile is 8 rows × 8 columns, so a decode-shaped matmul with M = 1 keeps 1 of 8 rows busy: at most 1/8 = 12.5% of the PEs ever do useful work. STRIP rewires the same 64 PEs into a 4 × 16 tile, so M = 1 keeps 1 of 4 rows busy (at most 25%), and each tile covers twice as many output columns, so the job needs half as many tiles. Each tile costs the same fixed time whether its rows are useful or not, `T_tile = L_SETUP + (L_RD + K) + (14 + L_PE) + T_DRAIN + L_RQ + L_WB` (T_DRAIN = 8 cycles FULL, 4 STRIP with int8 output), so `utilization = M·N·K / (64 · (L_ACCEPT + ceil(M/Rt)·ceil(N/Ct)·T_tile + L_DONE))` with (Rt, Ct) = (8, 8) for FULL and (4, 16) for STRIP. For `ffn_up` (K = 64, N = 256) at M = 1 the model gives FULL 7.1% (32 tiles × 112 cycles) versus STRIP 14.8% (16 tiles × 108 cycles), 2.07× higher. STRIP already fills every PE at M = 4; once M reaches 8, both modes fill all 64 PEs on every tile and need the same number of tiles (M·N/64), so both approach K / T_tile, held below 100% only by the fixed per-tile setup, fill/flush and drain cycles: at M = 64 FULL reaches 57.1% and STRIP 59.3% (1.037×); the only remaining difference is that STRIP drains 4 rows per tile instead of 8. The price of the split is operand bandwidth: STRIP reads 4 A + 16 W = 20 bytes per stream cycle instead of 8 + 8 = 16, which is 25% more.
